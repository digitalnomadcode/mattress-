# Архитектура VELORA

Один Next.js App Router проект: публичные страницы /ru и /kk, серверные API, закрытая /admin. PostgreSQL через PrismaPg; отдельный API-сервер не требуется. Vercel и Neon подходят для размещения; в облачные сервисы приложение пока не опубликовано.

## Данные и доступ

server/public-data.ts читает опубликованные активные варианты, остаток и настройки. React cache действует в рамках одного серверного запроса; страницы динамические. lib/catalog.ts используется для seed и просмотра без БД. Неизвестные характеристики остаются пустыми. Изменение цены не переписывает старые заказы.

NextAuth Credentials использует scrypt-хеши и подписанную 8-часовую JWT-сессию. Каждый защищённый запрос проверяет пользователя, disabled и sessionVersion в БД. OWNER меняет настройки; OWNER/MANAGER обрабатывают заказы, цены, продажи и возвраты; WAREHOUSE работает с поступлениями, корректировками, распределением и подсчётом. WAREHOUSE не получает список заказов и выручку dashboard. Открытой регистрации нет; первый OWNER создаётся отдельным скриптом из защищённых переменных.

Изменяющие API требуют точного совпадения Origin с NEXTAUTH_URL, JSON и серверную Zod-валидацию. Host/X-Forwarded-Host не используются как доверенный публичный адрес. Credentials-вход использует CSRF NextAuth; частота входа и оформления ограничивается атомарными счётчиками PostgreSQL.

## Транзакции

server/operations.ts фиксирует operation key, вид и SHA256 отпечаток данных. Advisory lock сериализует один ключ: одинаковый запрос возвращает сохранённый результат, другой payload получает конфликт. Операции склада берут общий транзакционный lock; для малого магазина это исключает гонки резерва, продажи, приёмки, возврата и подсчёта. Резерв дополнительно использует условный SQL UPDATE с проверкой числа обновлённых строк. При масштабировании на несколько складов потребуются более узкие блокировки.

Транзакция включает остаток, резерв, движение, состояние заказа и outbox-событие. SQL CHECK запрещают отрицательный остаток/резерв, reserved > onHand, некорректные цены, знаки движения и targets. Trigger запрещает UPDATE/DELETE StockMovement. Возврат ссылается на SALE, не превышает оставшееся количество исходной продажи и использует её цену.

## Заказы

- NEW: заявка сохранена, резерва нет.
- NEW → CONFIRMED: проверка версии/наличия, создание резерва.
- CONFIRMED → PROCESSING: резерв сохраняется.
- CONFIRMED/PROCESSING → DELIVERED: снятие резерва, списание и одна SALE на каждый OrderItem.
- NEW/CONFIRMED/PROCESSING → CANCELLED: освобождение резерва без продажи.
- DELIVERED и CANCELLED — конечные. Физический возврат оформляется отдельно; отмена доставленного заказа запрещена.

SKU, имя и цена сохраняются в OrderItem на момент оформления. Клиентские суммы игнорируются. Повтор конечного статуса не списывает товар снова. WhatsApp открывается пользователем, не подтверждает отправку и не меняет заказ. Онлайн-оплаты нет.

## Начальный остаток

89 известных SKU + 10 нераспределённых 90 см = 99. Идемпотентный seed импортирует текущий снимок через OPENING один раз. Историю 84 + 10 − 25 + 30 = 99 повторно не применять. У начального импорта нет цены продажи; в выручку он не попадает.

10 матрасов 90 см хранятся в UnallocatedStock с кандидатами 2601/2603. До уточнения они не продаются как известный SKU. Распределение создаёт парные ALLOCATION-движения, общий итог сохраняется. StockCount фиксирует учётный итог и физические количества по четырём зонам, не исправляя SKU автоматически.

## Отчёты и проверка

Деньги — целые KZT. Выручка = SALE минус RETURN с известными ценами. Графики группируют ввод движений по дням Алматы; даты неизвестных начальных продаж не выдумываются. Dashboard показывает последние 200 заказов/движений и 30 подсчётов; полный журнал доступен в Excel. Для больших объёмов нужны пагинация и фильтры дат.

Outbox сохраняет события, но отправщик n8n пока не реализован. Будущий worker должен дедуплицировать по ID и повторять доставку; webhook не должен напрямую менять склад или откатывать завершённую продажу.

Реальный PostgreSQL в тестах проверяет повторный seed, цену с сервера, конкурирующие резервы последней единицы, отмену, однократную доставку, возвраты, неизменяемость журнала, распределение и подсчёт. Браузерная проверка использует отдельную случайную схему и временных пользователей, проходит весь путь заявки и ограничения доступа. Внешняя БД для тестов запрещена. Рабочие данные тестами не очищаются.

Фотографии получены от владельца и встроены в каталог и галереи. Для публикации нужны защищённое создание владельца и production-БД/подключение Vercel. Неопределённые условия получения согласуются с менеджером; noindex сохраняется до завершения выпуска.
