# Публикация VELORA

Приложение использует Vercel + PostgreSQL. vercel.json задаёт Next.js, npm ci, регион fra1 и сборку с генерацией Prisma. Обычная сборка не запускает миграции или seed: повторный preview не должен изменять рабочий склад.

Для первого рабочего развёртывания предусмотрен явный одноразовый build-флаг VELORA_BOOTSTRAP=1. Он допускается только при VERCEL_ENV=production, отдельных TLS-подключениях Neon и защищённых учётных данных владельца. Сборка последовательно выполняет migrate deploy, идемпотентный seed, создание владельца, release:check и Next build. Ничего не публикуется при сбое шага. После активации удалить ADMIN_PASSWORD из настроек проекта и выполнить обычное развёртывание без bootstrap-флага. Пароль аккаунта остаётся в виде scrypt-хеша в базе.

Когда DATABASE_URL уже управляется чужой интеграцией, использовать VELORA_DATABASE_URL для магазина и DIRECT_DATABASE_URL для его миграций. Старые интеграционные переменные сохраняются без изменения. .vercelignore явно исключает локальные .env, сгенерированные файлы и зависимости из загрузки.

1. Создать отдельную production-базу PostgreSQL (например, Neon); для preview использовать другую базу/ветку. Для Neon DATABASE_URL — pooled URL с TLS, DIRECT_DATABASE_URL — direct URL с TLS. Не копировать локальный Docker URL или пароль в Vercel.
2. В защищённом окружении для production-базы выполнить npm run db:deploy и npm run db:seed. Seed однократный; не использовать reset/db push. Подтвердить, что исходный снимок 99 шт. по-прежнему актуален на дату запуска. Не распределять неизвестные 10 шт. по моделям без фактической сверки.
3. В том же защищённом окружении задать ADMIN_EMAIL и ADMIN_PASSWORD, выполнить npm run admin:create и убрать ADMIN_PASSWORD после создания. Пароль не отправлять через чат, репозиторий или параметры URL.
4. Импортировать digitalnomadcode/mattress- в Vercel. Приложение находится в корне репозитория. Node.js 24; Framework Next.js. Указать DATABASE_URL, новый случайный AUTH_SECRET и NEXTAUTH_URL — точный публичный HTTPS origin сайта. Нельзя использовать локальный signing secret в production. Vercel API token и Neon API key не нужны работающему приложению.
5. Выделить preview и production разные базы и настройки NEXTAUTH_URL. Настроить ограничение доступа к предварительному развёртыванию; noindex сам по себе не закрывает сайт от посетителей. Реальные заказы не оформлять в preview.
6. В окружении релиза выполнить npm run release:check. Проверка только читает конфигурацию, миграции, доступ владельца и сверяет склад/резервы с журналом. Она не применяет миграции, не создаёт пользователя и не публикует сайт.
7. Открыть обе языковые версии по HTTPS, выбрать размер, сохранить проверочную заявку и войти в админку. Для проверки доставки использовать отдельную тестовую базу. Проверить WhatsApp-ссылку без отправки сообщения, Excel и смену языка. Для домена подтвердить наличие домена и доступ к DNS; не придумывать доменное имя.

Адреса точек, условия доставки, гарантии и возврата владелец пока не предоставил. До уточнения показываются города, контакты и согласование получения с менеджером; подтверждённые условия добавляются по мере готовности. Фотографии получены из папки владельца и встроены в каталог. Отзывы ожидают реальных материалов. Индексация остаётся закрытой до завершения выпуска.

Для автоматического управления Vercel и Neon из этой среды нужны отдельные защищённые подключения к API. API token Vercel направляется только в api.vercel.com, API key Neon — в console.neon.tech. Их отсутствие не мешает локальной работе, но не позволяет агенту создать облачный проект и выполнить deployment.
